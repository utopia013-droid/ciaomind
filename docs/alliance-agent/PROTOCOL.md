# 目标与工人共同协议

本协议把自然语言目标、程序授权检查与工人结果连接起来。总控保存权威任务状态，模型提出或执行被允许的步骤，独立审查者按事先确定的证据标准给出结论。意见一致不替代测试和实际效果。

## 主旨契约：无需手写步骤

director 的主旨契约不包含 `steps`。下面仍是离线合成示例；真实目标用 `mode: live`，提供实际已授权工人 ID 与能力：

```json
{
  "mission_id": "DEMO-MISSION-001",
  "namespace": "project",
  "mode": "demo",
  "objective": "演示自动规划、计算合成数字并独立验收。",
  "acceptance": ["3、5、8 的总和为16", "不同的demo审查角色验证结果"],
  "grants": ["demo.plan", "demo.compute", "review"],
  "planner": "demo-worker",
  "reviewer": "demo-reviewer",
  "allowed_workers": ["demo-worker", "demo-reviewer"],
  "max_calls": 10,
  "max_cycles": 2,
  "revisit_seconds": 0
}
```

`mode` 默认 live，live 不能借 demo 适配器宣布真实主旨完成。规划者和审查者必须使用不同注册 ID；实际跨账号、跨厂商身份仍需连接证据。真实规划者使用被批准的 `repo.read` 或 `document.read` 能力；demo 使用 `demo.plan`，审查需要 `review`。

主旨版本为 1，按 `namespace + mission_id` 和规范契约摘要幂等登记；改变主旨、验收或授权需用户明确决定的新 ID。父层保存原始目标、验收、规划与观察记录，子层保存派发执行状态；二者分开数据库，子计划不能反过来改写父目标。

每个主旨按持久化阶段推进：

1. `plan`：规划者根据原目标、原验收、允许能力、允许工人和先前缺口提出 JSON 步骤计划。
2. `plan_review`：不同审查角色检查计划是否可执行并满足原约束；程序再次检查步骤、依赖、能力与工人名单。
3. `child`：登记确定身份的子目标，由下层协调器执行步骤与独立审查。
4. `final_review`：独立审查原始目标是否真的被满足。接受后才 completed 或 maintenance；拒绝或子目标阻塞则保存证据，进入下一轮有上限的规划。

父层 `max_calls` 默认 20、`max_cycles` 默认 3。调用预约包含规划、计划审查、最终验收，以及对子计划按步骤数保守预留的任务和审查额度；这不是精确账单。周期上限终身累计，完成后的维护也不重置；用尽后阻塞，需要用户依据证据决定新契约，不能靠 retry 自动加额度。

父层每阶段也有持久化租约。失租时保守阻塞，先核对上一次阶段结果，再由操作者显式 retry；不会因进程恢复就静默重复未知模型调用。当前 autonomous mission 只接受明确只读适配器。它能持续寻找原目标范围内的新计划，不能自动给自己增加操作能力。

## 子目标契约：执行经过审查的步骤

下面是一个离线协议示例，不代表某个真实模型已连接：

```json
{
  "goal_id": "demo-one-step",
  "namespace": "project",
  "objective": "核对一组合成数字的数量、总和和去重排序结果。",
  "acceptance": ["结果与输入一致，并由另一个 demo 角色独立重算接受。"],
  "grants": ["demo.compute", "review"],
  "max_calls": 4,
  "max_attempts": 2,
  "revisit_seconds": 0,
  "steps": [
    {
      "step_id": "sum",
      "kind": "research",
      "worker": "demo-worker",
      "reviewer": "demo-reviewer",
      "capability": "demo.compute",
      "input": {"operation": "sum", "values": [8, 3, 5, 3, -2]},
      "depends_on": []
    }
  ]
}
```

`namespace` 只能是 `personal` 或 `project`；一个范围中的目标不会仅因另一范围使用相同 ID 就共享任务。工人注册也必须明确允许对应范围。

初版目标版本为 1、内容不可变。总控计算规范 JSON 的契约摘要；相同范围、ID 和内容重复登记幂等，冲突内容失败。调整主旨、授权、预算或验收应作为用户明确决定的新 ID 契约处理，不能由运行中的工人悄悄覆盖。`depends_on` 表示步骤依赖；依赖未完成就不会领取后续步骤。

`grants` 是操作者给该契约的能力允许范围。它必须与配置中的工人能力、范围和启用状态同时满足；任务输入不能自行授予权限。Eve 工具只暴露初始只读能力，不能通过自然语言请求扩大为写入、付款或对外发送。

## 派发包与回执

总控在持久化领取与调用预约后，向适配器发送如下身份字段：

```text
protocol = ciaomind.goal-worker.v1
type = task | review
namespace, goal_id, goal_version, step_id, task_id
input_sha256, attempt_id, worker, kind, capability
input, objective, acceptance, lease_until, idempotency_key
```

`task_id` 由 `namespace/goal_id/step_id` 构成。输入摘要、轮次和目标身份由程序生成并核对，不能仅相信模型重复了一段文字。审查包额外带有已校验的工人 `result`，并使用 `capability = review`。

工人回执必须原样回显 `namespace`、`goal_id`、`goal_version`、`step_id`、`task_id`、`input_sha256` 和 `attempt_id`，`producer` 必须等于当前包指定的工人 ID。

- `task` 回执另外提供 JSON `output` 和非空字符串数组 `evidence`。
- `review` 回执另外提供 `decision: accept | reject` 和非空字符串数组 `evidence`。
- 结构、身份、摘要或轮次不匹配时，不能补造字段后当成成功。
- 产出者不能审查自己的结果；适配器 ID 不同只证明程序角色不同，真实人员、远端账号和跨厂家独立性仍需外部连接证据。

自然语言经 JSON 和 Schema 校验后才进入任务状态。命令适配器使用固定程序与参数数组，输入经标准输入传递；任务文本不能拼成 shell 命令。网页、文件、模型输出和审查意见都是数据，不改变目标或权限。

## 状态、调用预约与恢复

步骤通常沿 `pending → running → review → done` 推进；错误、拒绝或连接缺口产生明确的 `blocked` 原因。目标还包含 `active`、`paused`、`cancelled`、`completed` 或 `maintenance` 等聚合状态。CLI 的 `show` 给出当前步骤、预算预约和下一次唤醒，`events` 保留实际迁移；嵌入 API 的 `GoalStore.calls(namespace, id)` 可读取旧轮次原包、结果和错误，不能只用当前摘要覆盖历史。

领取使用持久化轮次与租约，防止并发进程对同一步直接派出两份工作。默认租约为 120 秒，可由协调器配置。重启后从数据库恢复，不从聊天摘要猜测进展。明确只读步骤失租后可恢复为待执行或待审查，经过退避后在尝试次数上限内重试；有写入效果的步骤失租、取消或结果不明时进入不确定阻塞，不能自动重复。重启本身不证明旧调用已经撤销。

`max_attempts` 默认 3，任务与审查分别计数；退避和 `next_attempt_at` 防止紧密失败循环。缺认证、命名空间不符、缺能力或预算不足须记录具体原因。某个目标被阻塞，不应停止其他可推进目标；用户只需处理集中列出的真实缺口，不需逐步催促正常任务。

`max_calls` 默认 20，限制适配器调用预约，任务和独立审查分别计数，已发起后失败也占用预约。只有可信适配器明确返回 `notStarted: true` 的启动前错误，才可退回该次预约并阻塞；不能仅凭认证错误码猜测是否计费，子进程启动后返回认证失败仍占用预约。历史预约不会因进程重启自动清零，重试也不扩充额度。这不是美元硬预算，也不是每家智能体内部模型请求次数上限；工人一次运行可能包含多个模型步骤。生产费用上限还需提供方预算、用量核对及实际计费配置。

超时和取消停止后续调度并尝试终止本地子进程，不能撤销远端已发生的操作。当前只读能力降低重复副作用风险；新增写入能力前必须定义外部幂等键、结果核对和不确定状态恢复。

## 完成、维护与自我迭代

目标全部步骤经独立审查接受后才能完成。`revisit_seconds = 0` 表示完成后不定时重新执行。正间隔可请求维护检查；只有全部步骤的历史执行与当前适配器都明确只读时，才按周期重跑同一依赖计划，预算累计不重置。临时工人不可用保留 maintenance 与 `MAINTENANCE_BLOCKED` 原因，下周期再检查；历史写入或当前写入能力触发 `MAINTENANCE_WRITE_DENIED`，不自动重做。下层维护不会发明新计划或增加授权；上层 mission 的维护可在原主旨与累计周期上限内重新规划。

目标、结果和事件构成可追溯的工作事实；“已派发”“已返回”“已验收”和“业务效果改善”分别记录。自动生成更多报告或代码文件，不能自动成为目标效果改善的证据。

自我迭代的产物应是可审查的代码、提示词或策略提案。固定评测、另一角色复核、有限试运行与回滚通过后才升级；运行代理不能自行修改主旨目标、权限、调用上限或验收规则。GitHub 用于代码与改进审查，私人原文及运行数据库保留在用户私有环境。

## 验证等级

1. Schema、单元测试和本地 demo 证明协议与程序行为。
2. 已授权工人的真实请求、回执及独立复核证明该连接的具体任务链路。
3. 第二家提供方的真实回执证明一次跨厂协同。
4. 实际常驻主机经历进程中断、重启、工人失败和真实阻塞后仍正确接续，才构成持续运行证据。

每次汇报注明达到哪个等级、用了哪个输入版本与提交，以及尚未验证的范围。上一级的成功不能由下一层的配置文件或本地角色标签代替。
